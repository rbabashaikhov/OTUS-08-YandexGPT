# Базовые примеры работы с YandexGPT

## `main.py`

Пример взаимодействия с YandexGPT через REST API.

Запрос формируется вручную с использованием библиотеки `requests`:

- задаётся endpoint API;
- формируются HTTP-заголовки;
- передаётся API-ключ;
- выбирается модель;
- задаются параметры генерации;
- передаётся список сообщений;
- обрабатывается JSON-ответ.

## `main_sdk.py`

Пример работы с YandexGPT через Python SDK Yandex AI Studio.

Используется пакет:

```text
yandex-ai-studio-sdk
```

SDK берёт на себя формирование запроса, авторизацию и обработку ответа модели.

## `main_sdk_chat.py`

Простой интерактивный чат с YandexGPT в терминале.

Чат:

- принимает сообщения пользователя через `input()`;
- хранит историю диалога;
- передаёт историю модели;
- сохраняет ответы модели в историю;
- поддерживает команду `/history`;
- поддерживает завершение через `exit` или `quit`.

Логика работы:

```text
Пользователь вводит сообщение
        ↓
Сообщение добавляется в messages
        ↓
История передаётся YandexGPT
        ↓
Модель генерирует ответ
        ↓
Ответ выводится пользователю
        ↓
Ответ добавляется в messages
```

# Домашнее задание: NER с помощью YandexGPT

## Цель

Разработать пайплайн извлечения именованных сущностей из юридических документов с помощью YandexGPT.

Пайплайн должен:

1. загружать юридические документы;
2. выполнять базовую предобработку текста;
3. отправлять документ и промпты в YandexGPT;
4. получать структурированный JSON;
5. очищать ответ от возможного лишнего форматирования;
6. преобразовывать JSON в словарь Python;
7. сохранять результат обработки.

# Работа с длинными документами

Первоначально использовалась простая стратегия truncation:

```python
text = text[:6000]
```

То есть модель получала только первые 6000 символов документа.

Во время тестирования выяснилось, что для судебных решений такой подход может приводить к потере наиболее важной части текста.

Типичная структура судебного документа:

```text
НАЧАЛО ДОКУМЕНТА
номер дела
дата
судья
участники
описание обстоятельств
мотивировочная часть
...
ПОСТАНОВИЛ / РЕШИЛ
итоговое решение суда
КОНЕЦ ДОКУМЕНТА
```

Резолютивная часть часто находится в самом конце.

На одном из тестовых документов модель получила только начало текста и извлекла возможную санкцию статьи:

```text
административный арест на срок до пятнадцати суток
```

вместо реально назначенного судом наказания:

```text
административный арест сроком на 13 суток
```

После анализа ошибки стратегия была изменена.

Для длинных документов сохраняются:

```text
первые 3000 символов
+
последние 3000 символов
```

Пример:

```python
MAX_CHARS = 6000


def prepare_text(text: str, max_chars: int = MAX_CHARS) -> str:
    text = text.replace("\xa0", " ")
    text = text.strip()

    if len(text) <= max_chars:
        return text

    half = max_chars // 2

    start = text[:half]
    end = text[-half:]

    return (
        start
        + "\n\n[... ЧАСТЬ ДОКУМЕНТА ПРОПУЩЕНА ...]\n\n"
        + end
    )
```

Это позволяет сохранить начало документа, где обычно находятся номер дела, дата и участники, а также конец документа с итоговым решением суда.

После изменения предобработки модель корректно извлекла фактический срок:

```json
"term": "13 суток"
```

# Prompt Engineering

Используются два отдельных промпта:

- System Prompt — определяет поведение модели;
- User Prompt — перечисляет необходимые сущности и формат результата.

## System Prompt

```text
Ты — точный AI-помощник юриста, специализирующийся на извлечении
структурированных фактов из судебных документов.

Твоя задача — извлекать только информацию, явно присутствующую
в предоставленном тексте документа.

Правила:

1. Не придумывай отсутствующие данные и не дополняй текст
   информацией из собственных знаний.

2. Если значение отсутствует в предоставленном тексте
   или его нельзя надежно определить, возвращай null.

3. Не восстанавливай анонимизированные данные.
   Значения вида <ДАТА>, <ФИО>, <НОМЕР>, <АДРЕС>,
   <ОБЕЗЛИЧЕНО> и аналогичные placeholders
   не пытайся расшифровывать или угадывать.

4. Не путай номера судебного дела с номерами протоколов,
   актов, постановлений и других документов.

5. Не путай дату текущего судебного документа
   с датами правонарушений, протоколов, проверок,
   предыдущих решений и других событий.

6. Не путай роли разных участников судебного дела.
   Определяй роль лица только на основании текста.

7. При извлечении статей закона используй только статьи
   и нормативные акты, явно упомянутые в тексте.
   Не добавляй статьи самостоятельно.

8. При извлечении результата рассмотрения дела используй
   фактически принятое судом решение.

9. Если в тексте присутствует резолютивная часть после слов
   "ПОСТАНОВИЛ", "РЕШИЛ", "ОПРЕДЕЛИЛ"
   или аналогичной формулировки, она имеет приоритет
   при определении решения суда.

10. Не путай фактически принятое решение суда
    с возможными санкциями, перечисленными в статье закона.

11. Не используй максимальный или минимальный возможный
    размер наказания вместо фактически назначенного судом.

12. Если в предоставленном тексте отсутствует резолютивная часть
    и фактическое решение суда невозможно надежно определить,
    возвращай null для соответствующих значений.

13. Ответ должен содержать только валидный JSON-объект.

14. Не добавляй Markdown-разметку, пояснения,
    комментарии или текст до и после JSON.

15. Не используй комментарии // или /* */ внутри JSON.

16. Используй двойные кавычки для ключей
    и строковых значений JSON.

17. Ответ должен корректно обрабатываться
    функцией json.loads() в Python.
```

# Очистка ответа YandexGPT

Несмотря на строгую инструкцию возвращать только JSON, во время тестирования модель иногда добавляла Markdown-разметку:

```text
```json
{
    ...
}
```
```

Поэтому функция `clean_response()` удаляет конструкции:

```text
```json
```

и:

```text
```
```

Также во время тестирования был получен ответ вида:

```json
{
  "document_date": null, // дата отсутствует
}
```

Такой текст визуально похож на JSON, но стандарт JSON не поддерживает комментарии.

При выполнении:

```python
json.loads(response)
```

возникала ошибка:

```text
JSONDecodeError
```

Поэтому в `clean_response()` также добавено удаление однострочных комментариев:

```python
re.sub(r"//.*$", "", text, flags=re.MULTILINE)
```

После очистки ответ передаётся в:

```python
json.loads()
```

# Обработка ошибок JSON

Парсинг выполняется через:

```python
def parse_response(response: str) -> dict:
    try:
        return json.loads(response)

    except json.JSONDecodeError as error:
        print("Ошибка парсинга JSON:")
        print(error)

        return {}
```

Это позволяет не останавливать весь пакетный запуск, если отдельный ответ модели оказался некорректным.

# Edge Cases и обнаруженные проблемы

Массовый тест показал, что даже при низкой температуре и достаточно строгом промпте LLM не всегда соблюдает заданную семантику полей.

## 1. Невалидный JSON

В одном из первых тестов модель добавила комментарий:

```json
"document_date": null, // дата отсутствует
```

Это привело к ошибке `json.loads()`.

Для обработки такого случая была добавлена дополнительная очистка ответа.

---

## 2. Ошибка из-за обрезки контекста

При первоначальной стратегии:

```python
text[:6000]
```

модель не увидела конец длинного судебного решения.

В тексте закона присутствовала возможная санкция:

```text
до пятнадцати суток
```

а фактически суд назначил:

```text
13 суток
```

Модель вернула первое значение.

После изменения стратегии truncation на сохранение начала и конца документа модель стала извлекать:

```json
"term": "13 суток"
```

Этот пример показывает, что качество NER зависит не только от промпта, но и от стратегии подготовки контекста.

---

## 3. Путаница `amount` и `term`

В одном из документов модель вернула:

```json
{
  "type": "лишение права управления транспортными средствами",
  "amount": "1 год 6 месяцев",
  "currency": null,
  "term": "1 год 6 месяцев"
}
```

JSON технически корректен, но значение срока ошибочно попало также в поле денежной суммы.

Это пример семантической ошибки, которую одного JSON-парсинга обнаружить нельзя.

---

## 4. Нарушение правила `null`

При отсутствии явного срока модель вернула:

```json
"term": "срок не указан в явном виде"
```

вместо:

```json
"term": null
```

Это показывает, что даже явно заданные в промпте ограничения не гарантируют полного соблюдения схемы.

---

## 5. Срок уплаты вместо срока наказания

В одном из документов для административного штрафа модель поместила в `term`:

```text
в течение 60 дней со дня вступления постановления в законную силу
```

То есть вместо срока наказания был извлечён срок исполнения решения.

Ответ связан с судебным решением, но семантически не соответствует назначению поля.

---

## 6. Анонимизированные данные

В RuLegalNER встречаются значения:

```text
<ФИО>
<ДАТА>
<НОМЕР>
<АДРЕС>
<ОБЕЗЛИЧЕНО>
```

Системный промпт запрещает модели восстанавливать такие значения по догадке.

Если значение невозможно определить, ожидается `null`.

---

## 7. Зашумленный текст

В исходных документах встречаются:

- лишние пробелы;
- неразрывные пробелы;
- ошибки форматирования;
- слитные слова;
- анонимизированные данные;
- нетипичная пунктуация;
- ошибки и опечатки в исходном юридическом тексте.

Несмотря на это, модель в большинстве тестов смогла извлекать основные сущности.

---

# Анализ подхода

## Преимущества LLM для NER

YandexGPT позволяет извлекать сложные сущности без обучения отдельной модели.

Плюсы:

- не требуется собственная размеченная обучающая выборка;
- набор сущностей можно менять через промпт;
- модель понимает контекст;
- можно извлекать не только простые имена и даты, но и более сложные сущности;
- можно определить роль человека из контекста;
- можно извлекать итоговое решение суда;
- ответ сразу можно получать в структурированном JSON.

Особенно полезна способность модели работать с сущностями, для которых недостаточно простого поиска по регулярным выражениям.

---

# Недостатки LLM-подхода

В ходе тестирования были обнаружены следующие ограничения:

- модель иногда нарушает требуемый JSON-формат;
- возможны семантические ошибки между полями;
- возможна генерация текста вместо `null`;
- возможна путаница между фактическим решением и описанием закона;
- качество зависит от стратегии truncation;
- результат не полностью детерминирован;
- каждый документ требует отдельного обращения к LLM API;
- необходимо дополнительно валидировать полученные данные.

---

# Сравнение с Natasha и spaCy

Классические NER-инструменты, например Natasha или spaCy, обычно работают быстрее и детерминированнее.

Для заранее известных сущностей они могут быть удобнее:

- ФИО;
- организации;
- географические объекты;
- даты;
- стандартные типы сущностей.

Также их использование не требует отдельного API-вызова для каждого документа.

Однако для специализированных юридических сущностей классической модели может потребоваться:

- собственная разметка данных;
- дополнительное обучение;
- создание правил;
- настройка специализированной модели.

LLM-подход позволяет описать новую сущность обычным текстом.

Например:

```text
фактически принятое судом решение
```

Это значительно сложнее выразить в классической NER-модели без дополнительного обучения или набора правил.

# Production-ready

YandexGPT уже может использоваться как компонент системы извлечения информации, однако одного LLM-вызова для production-системы недостаточно.

Более надёжный вариант:

```text
Документ
   ↓
Предобработка
   ↓
LLM
   ↓
JSON parsing
   ↓
Schema validation
   ↓
Business rules
   ↓
Готовые данные
```

Для production можно дополнительно проверять:

- типы полей;
- формат дат;
- денежные значения;
- допустимые валюты;
- соответствие `amount` числовому значению;
- отсутствие срока в `amount`;
- обязательные поля;
- соответствие решения резолютивной части документа.

Также можно использовать Pydantic или JSON Schema для строгой валидации результата.

# Установка

Проект использует `uv`.

Клонирование репозитория:

```bash
git clone https://github.com/rbabashaikhov/OTUS-08-YandexGPT.git
cd OTUS-08-YandexGPT
```

Установка зависимостей:

```bash
uv sync
```

# Переменные окружения

Для работы необходимо создать `.env`:

```text
YC_API_KEY=your_api_key
YC_FOLDER_ID=your_folder_id
```

Пример переменных находится в:

```text
.env.example
```

Файл `.env` содержит секретные данные и не должен попадать в Git.
